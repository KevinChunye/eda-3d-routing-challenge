Jiangbanya v5: six tiers (hard 1.3786, congested 1.3189, designs 1.4331, intro 1.1406, scale 1.1152, stress 1.0798)

Updates Jiangbanya from v3 to v5 on hard, congested and designs, and adds intro, scale and
stress. Aggregate = geometric mean over a tier's cases of (baseline delay / our delay), so
higher is better; every number below comes from `m3d/checker.py` through
`python -m m3d.cli leaderboard-all`.

Checks run on this branch: `scripts/check_submission_meta.py` (runtime metadata ok for 6
dirs), `scripts/verify_submissions.py` (658 route files, all legal),
`python -m m3d.cli leaderboard-all --check` (up to date). The PR changes only
`submissions/<tier>/Jiangbanya/**`, `LEADERBOARD.md` and the README leaderboard block.

**How it was run.** One run per case from the instance JSON alone (no routes from other
entries), seed 1, 4 threads, Intel Xeon @ 2.10 GHz (4 vCPU), 16 GB, one case at a time.
`runtime.json` is the wall clock of that run, instance JSON to `.sol.json`. One configuration
per tier; the router source is at the commit in each `meta.json` (`url`, `router_commit`).

**What changed since v3**
- Threshold acceptance that cools linearly to 0 (start 32 on hard, congested, intro, scale and
  stress; 8 on designs), with kicks and a return to the best solution.
- Hard, congested and the three new tiers: a discounted Thompson-sampling bandit picks the move
  type.
- Designs and the three new tiers: integer, goal-directed searches during negotiation and group
  repair, with exact shortest-path trees when a move is committed.
- The 4 threads adopt the best solution found so far: every fifth of the run (hard,
  congested), every 600 s (designs), every 120 s (intro, scale, stress).
- Congested: one 28,800 s budget split across the cases in proportion to their net count; the
  formula and the four limits are in `meta.json` as `time_limit_policy`.
- Stress: exact-reroute sweeps stop once fewer than 1% of nets improve, and no move starts that
  would cross the deadline.

The cloud VM restarted several times while congested case_03 was running; each time that case
was started again from scratch with the same settings. `runtime.json` holds the one
uninterrupted run that produced the submitted routes.
